核心

飞轮：每转一圈，baseline 更准

真相只有一份 living 文档。每轮迭代不重写它，而是写增量、上线、合并回去——下一轮从更准的起点出发。

baseline线上当前态真相
  1. 写 delta本轮需求 + 决策 + 埋点，落季度/版本目录
  2. 上线研发按 delta 实现并发布
  3. 补 changelog登记索引行，推进到「已合并」
  4. 反向合并手动改进 baseline 模块章，不重跑骨架
  5. 归档 delta整包归档，真相回到 baseline，进入下一圈
承重不变量 · 改 baseline 前先写 changelog 索引行，推进到「已合并」才动正文。日志权威，正文是可重建的缓存——脚本校验增量章是否真落进 baseline，整段漏搬亮红灯。

章节

两种 PRD 各装什么

同样追求「能直接喂研发做 spec」，但组织方式完全不同——一个按模块铺全量，一个按本轮变更写增量。

baseline按模块树 · 全量 · living

模块 = 主场景 A–F，子模块 A-1/A-2，每模块自带各端段

  1. 产品概览 + 术语词典是什么 / 黑话对齐
  2. 模块树 + 业务对象 + 状态机全集四支柱之三：编号 of record / 字段契约 / 迁移表
  3. 全局业务规则跨场景速查表 + 具名锚点
  4. 各模块章（Feed / 发布器 / 详情 …）每个 A-N 子场景的完整规则 + 字段 + 状态
  5. 埋点契约四支柱之四：事件表 + 归因
  6. 变更记录append-only changelog，承重不变量入口
delta9 章树 · 增量 · 单轮快照

按「本轮 N 需求 + 四支柱增量」组织，上线即合并归档

  1. 背景与价值论证WHY · 1.4 核心变更（vs 线上基线）
  2. 本轮需求只写真有改动的场景，未动场景整章删
  3. 业务对象增量 / 状态机增量 / 全局规则增量独立 H1 章，与 baseline 同构，反向合并直接搬章
  4. 决策记录多轮决策的来龙去脉
  5. 埋点本轮新增事件
  6. 排期 + 反向合并指引Phase / 依赖 / 合回哪些模块章

为什么这么切？好处是什么？

  • baseline 按模块、delta 按变更 — 研发看 baseline 一眼定位「这块功能现在长啥样」；看 delta 只关心「这轮要改啥」，不被未动场景的噪声干扰。
  • delta 只写真有改动的场景 — 「本轮不动 / 同上一版」这类占位句一律禁。PRD 是给研发对照实现的，未改章是噪声，让研发猜「这章在不在 scope」。
  • delta 的增量章与 baseline 同构 — 同套表头表行，上线后反向合并直接搬章，不用手工翻格式、不会翻错。
  • delta 引用 baseline 只锚场景编号 / 规则 ID — baseline 是 living 的，章节号会随合并漂移，编号才是稳定锚点，跨文档引用不会变死链。
  • 四支柱两边对齐（业务对象 / 状态机 / 全局规则 / 埋点）— 用业务语义精度而非技术黑话达到 spec coding，研发 AI 能反推 key 与 SQL。

状态词表 + 两层防线

状态取值是机械校验的依据，不能自由发挥。

delta 头部changelog 列含义
待排期 / 开发中规划中未上线，豁免合并检查
已上线已登记上线未合并 — 红灯窗口
已合并已合并反向合并完成

红灯 流程新鲜度：已上线 delta 必须合并，脚本 + hook + dashboard 三重兜底。  黄灯 内容新鲜度：模块章超 60 天未核对线上则提醒。
