## 一、12 章结构（锁定）

```
1.  项目背景与目标       1.1 现状分析 / 1.2 价值论证 / 1.3 目标+指标 / 1.4 核心变更 / 1.5 用户角色（含权限矩阵）
2.  场景地图            2.1 场景编号表 / 2.2 优先级 / 2.3 跨端数据流总览
3.  术语与业务对象词典    3.1 术语 / 3.2 业务对象 / 3.3 枚举 + 状态机
4.  全局业务规则         4.1 跨场景规则 / 4.2 归因规则 / 4.x 全局异常降级总则（接口超时 / 缓存兜底 / 承载方边界）
5.  前台功能需求         扁平子场景（5.1 / 5.2 / ...）
6.  后台功能需求         扁平子场景
7.  跨端/后端需求        扁平子场景
8.  通用文案清单         8.1 Loading/空/Toast / 8.2 弹窗 / 8.3 错误
9.  埋点与数据监控       9.1 事件 / 9.2 看板
10. 非功能性需求         SLA / 一致性 / 生效时效 / 并发
11. 里程碑与排期         Phase / 依赖 / 后续规划
12. 附录                兼容矩阵 / 旧版差异（按需）
```

### 章节编号硬规则

- **1-12 章编号固定，不能跳过**。即使某章内容很短（如 10/12 章），也必须有章节标题占位，内容可写「本期无特殊需求」。
- **5/6/7 章允许一层物理分组嵌套，禁两层**：父级 H3 `### 5.1 主舞台`（无场景号）+ 子级 H4 `#### 5.1.1 A-1 · 推流`（必带场景号 A-N / B-N / M-N / F-N）；禁 `##### 5.1.1.1` 两层嵌套。简单需求继续扁平 `### 5.1 A-1 · 发帖` 即可，不强制分组。
- **子场景标题必带场景编号 + 白话名**：`### 5.1 A-1 · 发帖`（h3 / h2 层级由 single/split 模式决定）。
- **§1.6 / §1.7 为可选章节**，模板见 `references/prd-optional-sections.md`，骨架不生成。PM 按需 copy 插入 §1.5 后、§2 前。

### 迭代版 PRD scope（重要）

迭代版 PRD（同一项目升版 V2 → V3 / V3.0 → V3.1）**只写本轮真有改动的场景**：

- ✅ 本轮新增 / 修改的场景 → 完整章节写规则 + 字段 + 状态
- ❌ 本轮未动的场景 → **整章删除**，不留「## 5.3 A-3 · 发帖（本轮不动）」类占位句
- ❌ 「本轮保持现状」「同 V2」「沿用线上」一句话占位章 → 禁

理由：PRD 是给研发对照实现的，未改章是噪声让研发猜「这章在不在 scope」。1.3 变更范围章已经声明 scope，正文不需重复声明「不改」。

### 1.4 核心变更的基线定义（重要）

**基线 = 当前线上运行版本，不是之前的 PRD 文档版本。**

- ✅ 线上已有该功能 + 本轮迭代部分行为 → 列【变更】/【新增】/【本期不做】三类
- ✅ 线上没有该功能 + 本期从零到一新建 → **全部【新增】，不写【变更】**；元数据表「线上基线」字段写「无（本期全新增）」；1.4 章标题保留「核心变更（本期全量新增）」即可，标题已表达全新增不要再用 blockquote 复述
- ❌ 拿之前的 PRD docx / wiki 历史版本（v3.4.docx / V2 wiki 页）当基线 → **错**，那是文档迭代不是线上迭代

判定简版：做完 demo 的人能不能在当前 App / 后台摸到这个功能？能 → 有基线，列变更；不能 → 无基线，全新增。

### 1.4 多轮决策迭代时的基线锁定（强制）

同一议题多轮决策（如 04-27 → 04-28 早 → 04-28 晚）写 1.4 时必须先收敛到**最终态**一行，不按时间堆三行迭代过程。1.3 / 1.4 锚点是 vs **wiki 线上基线**的 delta，迭代过程归 delta §6 决策记录。中间稿（自己几小时前的 PRD 草稿）绝不能当左列基线。

### 3.2 业务对象只写本期新增对象

3.2 章**只描述本期新增的业务对象**（如本期首次定义的"交易卡片"/"任务卡"等）。线上已有的业务对象（帖子 / 评论 / 用户 / 订单等社区 / 交易系统既有实体）直接不出现（章节标题 + 表格内容已隐含「本期新增对象」语义，不要用 blockquote 写「既有对象不重新定义」此类元信息），不脑补状态机 / 字段 / 生命周期（即便 baseline 里有现状描述，那是参考背景不是 PRD 的约束范围）。

3.3 状态机同理：只画本期新对象的状态迁移表，既有对象状态沿用现状。**不知道的就不要写**——写错的状态机比没写更糟（误导研发 + 需要倒回删改）。

### 骨架章禁 blockquote 导读（硬规则）

骨架章（1/2/3/4/8/9/10）**禁止用 `> ...` blockquote 写导读 / 引言 / 元信息**——标题已表达的内容不再复述，PRD-skill 填表规则（如 9.1「类型 = 既有/新增」）归 SKILL.md / references，不污染 PRD 正文。

**违例**：
- ❌ §1.4 开头 `> 线上社区目前没有交易卡片能力...全部场景均为新增...`（标题已写「本期全量新增」）
- ❌ §3.2 开头 `> 本期只新增 X 一个业务对象，既有对象沿用线上...`（标题 + 表格内容已隐含）
- ❌ §3.3 开头 `> 本期只定义 X 的类型枚举与状态迁移...`（同上）
- ❌ §4.2 末尾 `> L7 事件只负责归因，具体规则由 X 组定...`（归因边界放正文段落，不用 blockquote）
- ❌ §9.1 开头 `> 填表规则：类型 = 既有...直接抄 key...`（填表规则归 SKILL.md / references）

**合法**：5/6/7 章场景级 blockquote（业务范围声明 / 端兼容声明 / V1-V2 计划等有信息增量的）；user story 斜体引言 `> *...*`（按「PART / 场景用户故事陈述」规则，见 [artifact-conventions.md §五](../../../runbooks/artifact-conventions.md#五演讲叙事顺序所有-pipeline-skill-强制)）。

### 一点五、baseline / delta 两 profile 差异（老项目迭代）

上面 12 章结构 = 标准 delta / 普通 PRD profile。老项目持续迭代用 baseline 文档集模型（模型全貌见 [artifact-conventions.md §六](../../../runbooks/artifact-conventions.md)），baseline 与 delta 走不同规则集：

| 维度 | baseline PRD | delta PRD |
| :--- | :--- | :--- |
| 落点 / 命名 | 产品线根 `prd-{产品线}-baseline.md`，**无版本号** | `deliverables/{季度}/{版本}/`（如 `2026Q3/2.1.1/`，按季度 KPI 聚集，整包装 delta+imap+proto+assets） |
| 时态 | living，线上当前态全量真相 | 单轮迭代快照，上线后反向合并进 baseline 即归档 |
| 组织 | **模块树**（模块 = 主场景号 A-F，子模块 A-1/A-2），每模块章自带各端段 | 9 章树（1 背景价值 / 2 本轮需求 / 3 业务对象增量 / 4 状态机增量 / 5 全局规则增量 / 6 决策 / 7 埋点 / 8 排期 / 9 反向合并指引），按「本轮 N 需求 + 四支柱增量」组织 |
| scope | 全量（含线上既有，不删未动场景）| **只写本轮真有改动的场景**（§一「迭代版 PRD scope」铁律） |
| §X.Y 章节锚点 | **允许**（单文件 living，§4.2 具名锚点是合法内跳） | **单文件 delta 允许**（内跳合法）；仅 split（多文件拼接）禁（跨页死链） |
| 裸场景编号 | **允许**（模块树按场景编号索引是设计） | **单文件 delta 允许**；仅 split 禁（散件无上下文，用「编号 + 白话名」） |
| 1.4 核心变更 / 价值论证 / 里程碑 | 无（baseline 不讲单轮变更）| 有 |
| 变更记录章 | **有**（changelog 索引，append-only，承重不变量入口）| 无（delta 自己就是一次变更）|
| 四支柱 | 持**全量**（业务对象词典 / 状态机全集 / 全局规则 / 埋点契约）| 写**增量落独立 §3/§4/§5 H1 章**（与 baseline 对应章同构，反向合并直接搬章；本轮无变更则删该章），跨引 baseline 锚场景编号 / 业务规则 ID |
| check_prd_md.sh | 单文件天然豁免死链查（按是否有 `-scenes/` 判 IS_SPLIT，非 profile 名）| 单文件 delta 豁免；split delta 才查 §X.Y / 裸编号死链 |

两 profile 都要达 spec coding 规范——靠**业务语义精度**（字段契约 / 状态机 / 全局规则 / 埋点四支柱齐全，中文字段名 + 类型 + 约束 + 枚举写足），不靠技术黑话，研发 AI 反推 key / SQL。骨架生成 `gen_prd_skeleton.py --profile baseline|delta`。

### delta 按产物形状切「增量」（结构化互依整体的写法 · 强制）

「delta 只写增量」对**结构化互依整体**是错的：权限矩阵 / 状态机 / 档位表 / 字段表是当成完整格子读的，delta 只写片段 → 研发得翻 baseline 脑内打补丁才知道当前真相 = §4.6 叶子完整性在结构层的失败。按产物形状分两种写法：

| 产物形状 | delta 怎么写 | 反向合并动作 |
| :--- | :--- | :--- |
| **原子增量**（新增独立场景 / 业务对象 / 互不依赖的单条规则） | 只写增量本身 | **插入** baseline 对应章末尾 |
| **结构整体**（权限矩阵 / 状态机全集 / 档位阈值表 / 字段表等需整体读才有意义的） | 写**完整改后态**（整张矩阵 / 整张状态机）+ 顶部一句「本轮改动：X→Y」callout | **整块替换** baseline 对应章（callout 合并时丢弃，baseline 永远是干净全量、无版本标签） |

判定：研发只看 delta 这一段、不翻 baseline，能不能拼出完整可断言规格？能 → 原子增量；要脑补缺格 → 结构整体，写全量 + callout。§9 反向合并指引表「合并方式」列标「插入 / 整块替换」。

业内同构方案：DB schema migration 配 `schema.rb` 全量快照（真相只读快照不读 diff）、Terraform desired-state、合同 redline（全文 + 标注 → 接受修订 → clean 版）——都是「人改结构化产物时写全量 + 标注，下游读全量真相」。

### §2 本轮需求按迭代档位行文（`--tier` · 强制）

delta 先认档位（`gen_prd_skeleton.py --tier`），§2 按档位组织。这根轴与四支柱填充（§3/§4/§5）正交——档位只管 §2 排版，不决定四支柱有没有内容。

| 档位 | `--tier` | 触发 | 版本号 | §2 行文 | §3/4/5 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 补丁包 | `patch` | 散修复 + 小调，互不依赖 | x.y.z 三段 | §2.0 索引表（6 列，含修改点 / 验收）收口，仅重项另起 H3 | 通常删空 |
| 内聚特性 | `feature`（默认）| 单一能力，有新对象 / 状态机 | x.y 两段 | 平铺，按用户旅程顺序叙事 | 填实相关支柱 |
| 集合体 / 多团队 | `bundle` | N 个松耦合需求跨模块 / 团队 | x.y 两段 | 强制 §2.0 索引表 + 按单轴分组 H2 | 按需 |

**散需求（补丁包 / 集合体）行文铁律**：硬把无关需求串成一条叙事是假的——内聚单元是**分组 + 索引**，不是叙事。

1. **先地图**：§2.0 本轮需求索引表给读者一张全貌再散开。两档列不同——
   - 补丁包：`编号 | 需求 | 端 / 模块 | 修改点 | 验收 | 优先级`。**轻项在表里就讲完了**，不另起块。不放「反向合并目标」列：它与 §9 反向合并指引表重复（同一字段只写一次），且 §9 推 wiki 时整章剥离、该列却会留在 wiki 上把内部维护机制暴露给研发。
   - 集合体：`编号 | 需求 | 分组 | 反向合并目标 | 优先级`，「反向合并目标」列与 §9 呼应。
2. **后区块**：集合体按**单一轴**把需求拆成 `## 组 X · 组名` H2，每组归拢相关需求。分组**只许沿一条轴**：模块 > 用户旅程 > 跟版边界 > 团队，选让读者**跨引最少**的那条（多轴交织 = 读者反复跳，最差行文）。补丁包不强行拆 H2 组，一句话说明分组轴即可。
3. **补丁包默认全部进表，命中升块判据才起 H3**——骨架不再为每条需求预生成带槽位的块。**默认最轻、升块是加法**是承重设计：反过来（预生成四槽靠人删）必然被填满，规则写得再准也拦不住，这是 2.1.2.1 四条需求全填满四槽的实际教训。

   **升块判据**（任一命中即另起 `### 2.N`，模板在骨架 §2.0 表后的注释里）：新增 / 变更业务对象 · 涉状态流转 · 跨端行为不一致 · 有取舍要在 §6 决策记录交代。四条都不命中 = 轻项，读完表即止。

   重项块的槽位（现状 / 修改点 / 跨模块 / 数据影响）是**上限不是清单**，填到够用即止。一份补丁包里轻重项混装、套同一副四槽，正是它读着啰嗦的根：

   - **轻项**（前端修复 / 入口分流 / 默认值 / 纯文案，无业务规则 / 字段 / 流程变更）= **只占 §2.0 一行**，「修改点」格写 `做 X（原 Y 问题）`、「验收」格写判定点（`；` 分隔）。轻项不起块，所以下面这三样根本没有落脚处，也就不会写：
     - 「现状」——它只是「修改点」的否定式复述，读者两句得一句信息（`现状：没按认证态分流` + `修改点：按认证态分流` = 同一句说两遍）。前置态并进修改点那句的括号里。
     - 「跨模块 / 全局」写成 `属前端修复 / 不涉业务规则` ——这是给需求归类的元评论，不是"做到哪为止"的范围护栏。
     - 「数据影响：无新增数据」——没有数据变化就是没有，别留空槽占位。
   - **重项**（改业务规则 / 流程节点 / 字段口径 / 跨端 / 状态流转）= 另起 `### 2.N`，现状 / 修改点 / 跨模块 / 数据影响全保留，但：
     - **现状砍成一行前置态锚点**（具体场景号 / 字段 / 旧行为一句带过），不复述 §1 痛点已讲的、不重抄 baseline 现状章。
     - **跨模块只写"做到哪为止"的护栏**（`仅校验主题 / 简介 / 封面三类字段，其余不变` 是护栏；`属前端修复` 是废话）。
     - §2.0 表里该行「修改点」写一句话摘要、「验收」写 `详见 2.N`，编号空间与块共用。

   判定（写完一项回读，命中即塌回表里）：「现状」是「修改点」的反向改写 ／ 「跨模块」在说"这需求属于哪类"而非"做到哪为止" ／ 「数据影响」填的是"无"。`check_prd_md.sh` §1.6 按「块非空行 ≤ 14 且无表格 / 无数据影响」报 WARN 兜底，并查「详见 2.N」的悬空指针。

## 二、字段归属矩阵（核心规则，避免跨章重复）

| 字段类型 | 跨场景共用（写这里） | 场景独有（写这里 · 新模板 §4.1 三段式 + 数据影响 / 异常场景） |
| :--- | :--- | :--- |
| 业务规则 | 第 4 章 | 模块「显示逻辑」（可见性 / 权限 / 灰度等场景独有条件；命中跨场景规则只写「按 4.x 白话名」一句引用） |
| 状态机 | 3.3 业务对象状态机 | 模块「显示逻辑」里的状态分支描述（引 3.3 状态机） |
| 文案（Loading / Toast / 空态 / 错误） | 第 8 章 | 模块「显示要素」里本场景独有的按钮 / 标题 / 提示文案 |
| 数据字段映射 | 3.2 对象 → 数据源（宏观） | 模块「显示要素」逐项列字段 / 控件（微观） |
| 异常场景 | 第 4 章「全局异常降级总则」节（接口超时 / 缓存兜底 / 全站规则继承 / 承载方边界）| 「异常场景」表（仅 1–3 条场景独有 + 社区可控的项；写法见 `prd-scene-templates.md §4.3.1`） |
| 埋点事件 | 9.1 事件列表 | — |
| 归因窗口 / 漏斗口径 | 4.2 + 9.2 引用 | — |

**条件分支规则用可断言形式（可选档）**：第 4 章业务规则含条件分支 / 阈值档位 / 多业务态时，改「给定 ｜ 当 ｜ 则」三列表（模板 + 何时用 / 不用见 [`prd-scene-templates.md §4.5`](prd-scene-templates.md)），让条件→结果唯一可断言、分支可穷举（治下游歧义 / 遗漏）。无分支的纯陈述规则保持 bullet，不套壳。`check_prd_md.sh` 对全局规则章散文里挤 ≥ 2 个分支标记的 bullet 报 `branch_prose_hits` WARN。

> **字段命名立场（全文讲人话）**：业务对象词典（3.2）、状态机（3.3）、数据字段映射写**中文业务名 + 类型 + 约束 + 枚举**（如「主播 TRTC 标志｜布尔｜默认关」），不写 snake_case 研发 key（`trtc_enabled`）。spec coding 靠语义精度达成，研发 AI 反推 key。**唯一例外 = 埋点章（9.1 + §三点八）事件 / 属性英文名**——神策外部契约，已注册 key 不可翻译。业务方案专名（TRTC / OBS / RTMP）保留。
>
> **禁分号滥用（结构化优先 · WARN）**：单行 ≥ 2 个分号（全角 `；` / 半角 `;`）= 3+ 子句堆成一坨，读者得在长句里数边界。能用 bullet 或 `1. 2. 3.` 编号隔开就拆开写。`check_prd_md.sh` 报 WARN。**表格行豁免**——区块表 cell 内 `；` 是 `md_to_confluence.py` 切 `<li>` bullet 的约定分隔符，cell 里串 `；` 是正确写法（见 PRD SKILL.md Step 4）。
> ❌「提交认证触发申请事件；通过后置主播；标志默认关需加白；三组件全局默认开。」
> ✅ 改 bullet：`- 提交认证 → 触发申请事件` / `- 通过后置主播（永久）` / `- 主播标志默认关，需运营加白` / `- 连麦 / 策略卡 / 红包三组件全局默认开`
>
> **禁长句 run-on（拆句优先 · WARN）**：句段（两个终止标点 `。！？；` 之间）≥ 100 字 = 一口气读不完，读者要在逗号串里找主谓。拆成多句，或把并列项转 bullet / `1. 2. 3.` 编号。`check_prd_md.sh` 报 WARN（与分号校验互补：分号管「；」串，长句管「，」串 + 句子过密）。**表格行豁免**。
> ❌「显示逻辑：开始时间限 14 天内，结束时间为绝对时间到点仅提示，功能组件区按白名单只读反显，主播不可改、不可编辑已通过的预约。」（一句 50+ 字塞 4 条规则）
> ✅ 场景卡里 `显示逻辑 / 显示要素 / 交互` 是结构标签，**保留标签、冒号收尾，全部子句平级降为子 bullet**（父行别留正文）：
> ```
>    1. 显示逻辑：
>       - 开始时间限 14 天内
>       - 结束时间到点仅提示（绝对时间）
>       - 功能组件按白名单只读反显
>       - 已通过的预约主播不可改
> ```
> ❌ 非对称错法：父行留一句 + 剩下降级（`显示逻辑：开始时间限 14 天内` 后跟 3 条子 bullet）——要么全留父行、要么全降级，别一半一半。
>
> **禁 bullet 串句（一个 bullet 只扛一个原子断言 · WARN）**：一个 bullet 是一条独立断言，写完句号应落在**行尾**。句号出现在 bullet 行中间、后面还跟着实质内容 = 把好几条本该各自成行的并列项硬焊进了一行——这是最常见的 aislop 写法：能拆成 N 行的 `键 = 值 / 定义项`，却用句号串成一段散文，读者得在密集句号里自己切边界。**句号后面还有话，几乎等于"我把好几条 bullet 偷偷塞进了一行"**。一项一行、句号只落行尾。`check_prd_md.sh` 报 WARN（与分号 / 长句互补：那两条管「单行太挤」，这条管「并列项该拆没拆」）。**表格行豁免**（cell 内 `；` 切 bullet）；**冒号引子 bullet 豁免**（如「总根数 50 根。窗口规则分三种情况：」是概述 + 引出，句号在中合法）。**决策 / 埋点章无整章豁免**——决策流水也配写好看，`方案。理由。阻塞。` 3 句焊一行照样报，拆成「标签：」+ 子 bullet 更清晰（章节豁免只给「长句 ≥100 字」那一维，论证句可以长）。**叙事 / 论证标签对自动豁免**——以 `现状 / 现状问题 / 本轮 / 本轮不做 / 背景 / 痛点 / 取舍 / 理由 / 待拍 / 承接关系 / 影响面 / 方案 / 阻塞` 标签开头的 bullet（加粗或裸标签），「现状：X。本轮：Y」「取舍：论点。论据。」句号分段是因果对照 / 论点→论据，checker 自动豁免不报。**边界：仅 ≤2 句号算叙事 / 论证对**；同一 bullet 塞 ≥3 句号 = 标签下焊多件独立事，不再豁免、仍报仍拆成标签 + 子 bullet（与 `check_bullet_density` block 阈值对齐）。
> ❌「打点时间口径 = 成交时间。B 点（绿，买入方向：现货买入、合约开多 / 加多）。展示位置 = 预览块 + 帖子详情卡。数据源 = 交易线 binlog 异步落库，仅已分享用户，保留 3 个月。」（一个 bullet 句号串了 4 个独立定义项）
> ✅ 一项一 bullet：
> - `- 打点时间口径 = 成交时间`
> - `- B 点（绿）= 买入方向：现货买入、合约开多 / 加多 / 平空 / 减空`
> - `- S 点（红）= 卖出方向：现货卖出、合约平多 / 减多 / 开空 / 加空`
> - `- 展示位置 = 预览块 + 帖子详情卡（Feed 极简卡不展示）`
> - `- 数据源 = 交易线 binlog 异步落库，仅已分享用户，保留 3 个月`
> ❌「合约已平仓翻态（降级查询）：社区消费时先查当前持仓接口，未命中再调历史仓位批量查询接口，翻态发生在查询时（非推送）。卡片在平仓 / 强平时定型。」（fallback 流程 + 一个无关结论焊一行，且尾句与状态机表重复）
> ✅ 流程拆步骤、无关结论各自成行：**父 bullet 写规则名 + 冒号领起子 bullet**，子项写 `先查当前持仓接口 → 未命中 → 调历史仓位批量查询` / `翻态在查询时发生（非推送）` / `卡片在平仓 / 强平时定型`（若已在状态机表写过则删，不重复）。这是「维度 / 规则有多个独立子论点」的**首选范式**（替代分号 / 句号粘一行），不限于本例补救 —— 通用判定见 artifact-conventions §二。
> ✅ **对照参考——写得对的 bullet**（无句号串，一项一行）：`- 合约未实现盈亏（实时）=（当前价 − 入仓价）× 持仓数量 × 方向系数（多 +1 / 空 −1）` / `- 现货总收益（快照）= 累计已实现盈亏 + 当前持有的未实现盈亏`——公式各自成条，这才是 PRD 该有的样子。
>
> **拆完选列表类型——顺序是内容属性，不是排版偏好**：拆散一坨后用有序 `1. 2. 3.` 还是无序 `-`，按语义定，别为「满屏 bullet 太单调」滥用编号。**有序 `1. 2. 3.` 只在三种情况**：① 有先后 / 时序（主流程步骤、状态流转、操作顺序）② 有优先级 / 排名（P0 > P1、按重要性）③ 正文要回指编号（「如第 2 条」「满足条件 3 时」）。**其余全用无序 `-`**：并列字段枚举、互不依赖的规则、平级取舍点——它们没顺序，标 1/2/3 会暗示「有先后」，读者误按序理解。给并列项标编号 = 假的顺序信号，比单调更糟。真要破单调靠**层次**（加粗标签引子 + 子 bullet / 表格承对照 / 小标题分段），不靠切换列表符号。
> - ❌ 并列取舍点标编号：`1. 合规是底线` / `2. 前置成本更低` / `3. 兜底靠风控开关`（三条无先后，编号误导）
> - ✅ 并列用 `-`：`- 合规是底线` / `- 前置成本远低于事后处置` / `- 兜底靠 D-5 全局开关`
> - ✅ 时序用编号：`1. 进入开播 → 2. 选推流方式 → 3. 下发 OBS 密钥`（第 1 步做完才第 2 步，编号是真信号）
>
> **三条 WARN 共同底线——别换标点绕检测**：分号 WARN、长句 WARN、bullet 串句三条数的是句号 / 分号 / 长度，数不到逗号 / 顿号。把多件独立事从分号改成逗号 / 顿号焊同一行只是骗过 checker，认知负荷更高、违背规则本意。该不该拆看语义（多件独立事 vs 一件事的子项），不看凑没凑过阈值。权威定义 + Red Flags 见 `.claude/runbooks/human-voice-rules.md ⑥`。

**10 列填表模板**：

| 所属页面 | 事件中文名 | 事件英文名 | 属性中文名 | 属性英文名 | 数据类型 | 是否必填 | 数据值示例 | 应埋点平台 | 触发机制 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Feed 流 | 内容曝光 | `app_recome_content_show` | 内容类型 | content_type | STRING | 是 | community / news / article | APP / Web | 视区可见 ≥ 1s |

- 多属性事件每属性一行（md 不支持 rowspan），事件名 / 触发机制重复，数据团队接收时按事件英文名 group
- 事件英文名用 backtick 包裹，属性英文名不包

- 数据值示例：STRING 枚举类填 probe 拉到的真值（`A / B / C` 用 ` / ` 分隔），ID / NUMBER / BOOL 类神策不返候选值，写 `—`

**新事件命名约定**（与神策现有命名风格对齐）：

- 事件英文名前缀按行为：`pageview_` 曝光 / `appclick_` App 端点击 / `webclick_` Web 端点击 / `app_*_submit` 提交 / `app_*_success` 成交回传 / `app_*_status` 服务端状态 / `cms_*` CMS 操作
- 事件英文名结构：`{前缀}_{模块}_{动作}`，如 `appclick_card_trade` / `pageview_order_entry`
- 属性英文名：能复用神策已有字段（`platform_type` / `is_login` / `liveid` / `upid` / `contentid` / `uid` / `communityId` / `TransPair_current_id`）就不新建
- 新建属性英文名：snake_case 全小写优先；命中神策驼峰历史习惯（`commentNum` / `giftId` / `liveTime`）保持一致就好，不强求统一

**章节边界**：

- §9.1 事件清单：10 列模板
- §9.2 看板指标：业务口径表，写「计算口径」用事件中文名（「卡片 CTA 点击事件去重用户 / 帖子详情曝光事件去重用户」），不写裸 L1-L7 缩写
- §1.1 现状段 / §1.2 价值论证：引用神策已注册事件 key + 时段量级（追溯性强）

### 行内版本流水标签禁用

**禁在表格 cell / 场景描述 / 字段列表里加「（新增）」「（变更）」「（本期新加）」「（2026-05 新增）」等行内版本标签**。会被 `date_tag_hits` 规则抓 FAIL。

- ❌ 埋点表「卡片 CTA 点击（新增）」
- ❌ A-2 发布器「交易卡片入口按钮（新增，沿用工具栏视觉规范）」
- ❌ 表头「新增字段」列 + cell 打 ✓

正确写法：**版本 delta 集中在 §1.4 核心变更**里列清单（【新增】/【变更】/【本期不做】），表格 / 场景内部不重复打标。本期新增的埋点 / 场景 / 字段，PM 在 1.4 里说过一次，后续章节就用「写」不用再打「（新增）」标记。

理由：PRD 是稳态文档，上线后是业务的长期参照；「（新增）」标签随时间推移变成噪音（「这个新增是相对哪个版本的？」），且同一文档里有 10 个「（新增）」标签时等于没标。集中到 1.4 + 元数据表「线上基线」字段，可读性反而更好。

## 六、single vs split 模式的结构约定

### Single 模式（场景 ≤ 10）

```
deliverables/
├── prd-{简称}-v1.md          # 12 章全在一个文件
└── assets/                    # 所有截图
    ├── scene-A-1-wireframe.png
    └── ...
```

- 5/6/7 章的子场景直接 h3：`### 5.1 A-1 · 发帖`
- 单文件总行数目标 ≤ 1500 行；超了触发 `split_prd.py` 迁移提醒

### Split 模式（场景 > 10 或 PM 显式指定）

```
deliverables/
├── prd-{简称}-v1.md              # 主骨架（1-4 章 + 8-12 章 + 5/6/7 章标题 + 场景引用列表）
├── prd-{简称}-v1-scenes/
│   ├── front-A-1-发帖.md           # 子场景独立 md，~80-150 行
│   ├── front-A-2-删帖.md
│   ├── back-M-1-白名单.md
│   └── cross-F-1-推荐加权.md
└── assets/
```

主骨架 5/6/7 章示例：

```markdown
# 5. 前台功能需求

- [5.1 A-1 · 发帖](./prd-{简称}-v1-scenes/front-A-1-发帖.md)
- [5.2 A-2 · Feed 流](./prd-{简称}-v1-scenes/front-A-2-Feed流.md)
```

子场景文件内部：

```markdown
## 5.1 A-1 · 发帖

（5 段式完整内容，不再写 h1）
```

- 子场景文件命名：`{view}-{编号}-{白话名}.md`（空格用连字符）
- 子场景文件内部一级标题走 h2（`## 5.x`），避免 compose 拼接后变成双 h1

### View 前缀映射（多 view 业务可覆盖默认）

`split_prd.py` 默认按 12 章模板章节映射 view 前缀：5=front / 6=back / 7=cross / 4=ch4。

**多 view 强联动业务**（直播 / 社交 / 跨端协作类 —— 观众 + 主播 + CMS 三方都是核心 view）可以传 `--view-map` 覆盖默认值：

```bash
python3 split_prd.py prd-livestream-q2-v3.0.md \
    --view-map "4=broadcaster-h5,5=audience,6=broadcaster-web,7=cms"
```

按 view 切分文件名，PM 编辑时一眼分组。但 PRD 章节大纲本身**仍按 12 章模板组织**（§5 前台 / §6 后台 / §7 跨端）—— view-map 只影响文件名前缀。

### Confluence 推送：父页 + N 子页

`md_to_confluence.py --split-children-by-chapter` 支持 split 模式下推为「父页 + 各章节子页」结构：

- 父页：主 md 内容（§1-3 + §8-12 + §4-7 章引用列表，引用链接推送时自动改写为子页 URL）
- 子页：每章一个（§4 / §5 / §6 / §7），含该章下所有场景文件 inline 串接
- 子页 title = 章节白话标题（如 `观众端详细需求（Part 1）`）

**跨章引用的死链问题（split 模式落地 Confluence 后）**：

| 引用类型 | 在 Confluence 子页里 | 推荐处理 |
|---|---|---|
| 同子页内（§5.x → §5.y） | ✅ markdown anchor 可点 | 保留章节号 + 白话名 |
| 跨子页 / 父页（§5.6 → §10 / §2.4 / §11） | ❌ 章节号是死链，读者点不到 | **不写章节号引用** → 关键约束 inline 重述在子文件里（容许少量重复，子文件自洽） |

子文件示例（A-1 直播间完整全貌的「系统检查」段）：

```markdown
**系统检查**

- 拉流方式按客户端版本路由：新版本走 TRTC Mobile SDK 低延迟拉流（≤ 1s），老版本走 CDN 拉流（≤ 3s）
- TRTC 连接失败自动降级 CDN，用户无感
- 灰度期 5%、全量期 100% 新版本走 TRTC

# ❌ 不写：「TRTC 拉流策略详见 §10 非功能 + §2.4 并存过渡期」
# 因为 split 子页和父页在 Confluence 是不同 page，章节号无法跳转
```

### 模式切换

- `gen_prd_skeleton.py` 读对应项目 `scene-list.md` 的场景数：≤ 10 → single，> 10 → split
- `--mode {single|split}` 强制指定
- `split_prd.py <prd.md>` 把 single 模式的 md 拆成 split 结构（一次性迁移）
- `prd_compose.py <prd.md>` 把 split 结构拼回完整 md（compose 模式 push 前自动调，也可手动跑预览）

### 编辑粒度 vs Confluence 推送粒度（解耦）

| 维度 | 粒度 | 工具 |
|---|---|---|
| PM 本地编辑 | 一个场景一个文件（split 出 N 个，N 通常 10-30） | `split_prd.py` |
| Confluence 推送 | 一个章节一个子页（4-N 个子页，N 通常 3-5） | `md_to_confluence.py --split-children-by-chapter` |

**不要把"编辑粒度的 N 个场景文件"直接当成"Confluence 上的 N 个子页"** —— 子页太碎不利浏览（目录树过长 + 单页内容过短独立成页不划算）。

## 七、图片约定

- **相对路径**：md 里写 `./assets/xxx.png`（不写绝对路径，不写 http URL）
- **命名**：`scene-{编号}-{类型}.png`（类型：`wireframe` / `final` / `flowchart` / `screenshot`）
  - 例：`scene-A-1-wireframe.png` / `scene-M-1-final.png` / `arch-flow.png`
- **DPI**：≥ 144（Playwright 默认 72；prototype skill 截图脚本默认输出 144 dpi）
- **alt 文本**：必须有，写场景名或功能描述（空 alt 被 check_prd_md.sh 拦）
- **caption**：可选，写在图下方单独一行 `*caption 文本*`（斜体）
- **Confluence 上传**：push 时 `md_to_confluence.py` 自动上传本地图为 attachment 并改写路径，PM 无感

## 八、命名 / 术语一致性

### 文件命名

- 主 md：`prd-{产品线简称}-{项目简称}-v{版本}.md`
  - 例：`prd-community-v1.md` / `prd-activity-v5.md`
- 归档：升版时旧版进 `archive/`，新版覆盖原文件位置
- 老 docx 归档进 `archive/legacy-docx/`（不再触碰）

### 术语一致性（跨所有章节）

- 每个业务对象 / 状态 / 枚举只定义一次（第 3 章），所有后续章节引用**一字不差**
- 禁同义词并存：在 3.1 术语表里定「帖子」→ 所有章节禁出现「动态 / 内容 / feed 条目」
- 由 `humanize/structural.py` 扫描兜底（禁用词列表配置在 `patterns.py`）

## 九、自检清单（PM 交付前过一遍）

1. **结构完整**：`check_prd_md.sh <path>` 通过
2. **无裸场景编号**：正文 grep `A-[0-9]` / `B-[0-9]` / `M-[0-9]` / `F-[0-9]` 无命中（只能在 heading / 表格左列 / 埋点名出现）
3. **5 段式字段名锁定**：`grep -E "^- \*\*(触发|读|写|事件|API)" <path>` 无命中（这是研发字段，PM 应用业务语言）
4. **图片路径有效**：所有 `![](./assets/...)` 对应的文件存在
5. **CJK 标点规范**：`python3 scripts/check_cjk_punct.py <path> --strict` 通过
6. **无圈数字**：`grep -E "[①②③④⑤⑥⑦⑧⑨⑩❶❷❸❹❺]" <path>` 无命中
7. **术语一致**：3.1 定义的术语在后续章节用法一致（无同义词并存）
8. **跨章引用用白话**：所有 `见 X.Y` 引用均含白话名（`见 4.1 一帖一卡` 而非 `见 4.1`）
9. **条件分支规则可断言（可选档）**：第 4 章含条件分支 / 阈值 / 多业务态的规则用「给定 ｜ 当 ｜ 则」三列表（见 `prd-scene-templates.md §4.5`），条件→结果唯一、分支穷举（覆盖所有枚举 + 空态 + 异常态）；`check_prd_md.sh` 的 `branch_prose_hits` WARN 兜底，纯陈述规则误报手动忽略
