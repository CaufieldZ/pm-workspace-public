# PRD 写作指南

写 PRD 前读这一页。SKILL.md 讲规则和流程，这里讲每章怎么写，每处都附示例。照示例的形状写，比自己发挥更稳。

## 一、读者和标准

读者是开发、开发用的 AI、测试。他们按文档做事，会逐句当真。

好文档的标准：

- 读一遍就知道做什么、做到哪、怎么算做对
- 每件事只在一个地方写，找得到、不打架
- 没有读了也不影响开发的段落

## 二、delta 各章写什么

| 章 | 写什么 | 篇幅 |
| :--- | :--- | :--- |
| 协作头 | 骨架自带的表，填人名和状态；不知道的保持占位 | — |
| 1. 概述 | 要解决的问题、本轮做什么、成功标准（指标 + 目标值），各一两句；范围表（模块 / 本轮改动 / 实施方）；不做；待确认 | 半页以内 |
| 2. 本轮需求 | 按模块或页面分块，见第四节 | 主体 |
| 3. 业务对象增量 | 本轮新增或变更的对象和属性 | 没有就删章 |
| 4. 状态机增量 | 本轮新增或变更的状态流转，见第五节 | 没有就删章 |
| 5. 全局规则增量 | 两个以上模块共用的规则 | 没有就删章 |
| 6. 决策记录 | 输入里给过理由的取舍，一行一条，见第七节 | 推 wiki 时剥离；没有就删章 |
| 7. 埋点与看板 | 10 列事件表 + 指标口径，见第八节 | — |
| 8. 排期 | 骨架自带的表 | 推 wiki 时剥离 |
| 9. 反向合并指引 | 上线后合进 baseline 哪一章、插入还是整块替换 | 推 wiki 时剥离 |

删章时连章标题一起删，剩下的章号不用改。需要竞品参考或多方案对比时，按 `prd-optional-sections.md` 加在 §1 末尾。

## 三、§1 概述怎么写

示例（直播策略卡悬浮窗升级）：

```markdown
# 1. 概述

- **要解决的问题**：观众端策略卡一次只显示一张、过一会儿自动收起，主播一场想推几个币，观众翻不到，收起后也找不回。
- **本轮做什么**：观众端悬浮窗支持翻看多张在架卡，新增限价挂单卡、带单项目卡两种卡。
- **成功标准**：策略卡点击率 3.1% → 5%；策略卡带来的合约下单人数提升 30%。

**范围**

| 模块 / 页面 | 本轮改动 | 实施方 |
| :--- | :--- | :--- |
| 策略卡悬浮窗（D-1 / D-6 / D-7） | 多卡翻看，新增两种卡 | 直播客户端（App / Web） |
| 卡片状态与快照 | 推送完整快照 | 直播后端 |
| 主播端推卡 | 本轮另出文档 | 直播 Web 工作台 |

- **不做**：主播端推卡界面（另出文档）。

**待确认**

- 从卡面跳到合约交易大厅后，直播声音是否继续，取决于客户端能力，上线前确认
```

要点：

- 成功标准照抄输入里的数字；输入没给数字，写「待确认」，不自己编目标值
- 范围表每一行对应 §2 的一个模块块（或明确由别的团队、别的文档负责）
- 「不做」只写容易被误以为要做的事；没有就删这一行

**待确认写什么**：开发不问清楚就没法写代码或写用例的点，而输入里没给答案。包括：输入里自相矛盾的地方（写清两种说法）、输入明确说「待定」「你看着办」的、失败或异常时怎么处理但输入没说的。不写进待确认的：自己能从输入推出来的、与本轮无关的、评审建议（只在对话里提给 PM）、输入已经回答的、规格或原型里已定下的默认做法。

## 四、§2 模块块怎么写

**一个模块一块。** 开发会当成一个组件做的，就写成一块。几个场景是同一组件的不同情况（合约 / 现货、普通用户 / 带单员），合成一块，不同的地方放进差异表。块标题写模块名，覆盖的场景编号写在括号里。

**块里有四样东西，按需要出现：**

1. 图：有原型截图时用骨架的左图右文表（左图右规格），没有图就直接写条目
2. 规格：一条一件事，写成「条件 → 结果」或「对象：取值」
3. 差异表：同一模块有几种情况时，行是不同的项，列是各种情况；相同的项写在上面的规格里，不进表
4. 验收：三到五条，只写最容易做错的判定点：临界值、情况之间的差别、不该发生的事

**差异表的列要齐。** 先把所有情况列出来再画表：本轮新增的、线上已有的都算一列。线上已有的那种（比如原来就有的市价卡）没有新场景编号，最容易被漏掉。

**数字写一次。** 阈值、次数、时长只在它所属的那条规则里出现。要说明哪些可配置，写参数名（「分流阈值可后台配置」），不再写一遍数值。

**多个模块用到的规则写进 §5。** 模块里写规则名就够了（「发布后按『来源页回跳』规则返回」）。

**失败和异常**：输入给了处理方式的，写在相关那条规格里；输入没给、但开发必须知道的，写进 §1 待确认。不自己编重试次数、提示文案、降级方案。

**引用写全名。** 「见 2.3 盈利顶飘」「按『来源页回跳』规则」，被引用的标题或规则名必须真实存在；不写「见上文」「见补充说明」这类找不到落点的引用。

**示例：盈利顶飘**（合约 / 现货两条链路 × 普通用户 / 带单员两种身份）

按场景逐个写会写成四个块，每块都重写一遍承载形态、自动消失、频控和「不再显示」，再加上 §5、§6 里又各写一遍，同一件事讲了八遍左右，还写出了矛盾。按模块写，是下面这一块：

```markdown
## 2.3 盈利顶飘（T-6 ~ T-9）

- 交易大厅顶部的非阻断浮层，不遮挡下单和持仓操作区；5 秒无操作自动消失，可点 × 关闭
- 本次成交产生正的已实现盈亏才出；亏损、零盈亏、强平结算不出
- 带单员在普通大厅不出顶飘，只在带单交易界面出
- 勾选「不再显示」后不再出，可在交易偏好设置重新开启
- 点「我要晒单」进发布器，自动带上对应卡片；发布成功后回到弹出顶飘的界面

**差异**

|  | 合约 · 普通用户 | 合约 · 带单员 | 现货 · 普通用户 | 现货 · 带单员 |
| :--- | :--- | :--- | :--- | :--- |
| 出现在 | 合约交易大厅 | 带单交易界面 | 现货交易大厅 | 现货带单交易界面 |
| 触发 | 平仓，含止盈止损、部分平仓 | 同左 | 卖出，含止盈止损；清仓卖出不出 | 同左 |
| 展示 | 交易对与合约类型、方向、杠杆、仓位模式、本次盈亏 | 同左 | 交易对、本次盈亏 | 同左 |
| 按钮 | 盈利 < 1000 USDT 出「我要晒单」，≥ 1000 出「申请成为带单员」 | 只有「我要晒单」 | 同合约普通用户 | 只有「我要晒单」 |
| 晒单带的卡 | 完整平仓带已平仓卡，部分平仓带持有中卡 | 带单项目卡 | 现货持有卡 | 带单项目卡 |
| 频控 | 每日 3 次，同交易对 30 分钟内不重复 | 同左 | 每日 10 次，同交易对 10 分钟内不重复 | 同左 |

分流阈值、自动消失时长、两套频控都可后台配置。顶飘上的本次盈亏和卡片上的盈亏口径不同，数字不一致属正常。

**验收**

- 盈利 999.99 USDT 出「我要晒单」，1000.00 出「申请成为带单员」
- 合约当日第 4 次、现货当日第 11 次盈利不出顶飘
- 部分平仓后晒单，带的是持有中卡
- 带单员在普通大厅平仓盈利，不出顶飘
```

## 五、§4 状态表怎么写

**一行只写一个对象从一个状态到另一个状态。** 第一行从「不存在」写起。一个动作同时改了两个对象的状态（比如推新卡：新卡进入讲解中，原来讲解中的卡降为在架），拆成两行，触发写同一个动作：

```markdown
| 起始状态 | 触发 | 终止状态 | 谁触发 |
| :--- | :--- | :--- | :--- |
| 不存在 | 主播推出新卡 | 讲解中 | 主播 |
| 讲解中 | 主播推出另一张新卡（本卡被替下） | 在架 | 主播 |
| 讲解中 | 主播点「停止讲解」 | 在架 | 主播 |
| 在架 | 主播点「设为讲解」 | 讲解中 | 主播 |
| 讲解中 / 在架 | 主播点「收回」 | 已收回 | 主播 |
| 讲解中 / 在架 | 主播结束直播，或运营强关直播间 | 已收回 | 系统 |
```

表后写约束（数量上限、终态不可逆、什么情况不触发），一条一行：

```markdown
- 讲解中最多 1 张，可以为 0 张；讲解中 + 在架最多 3 张
- 已收回是终态，要再推只能推一张新卡
- 推流中断不触发收回
```

写完逐行自查：

- 每一行的起始状态和终止状态不同（状态不变的事写在约束里，不进表）
- 「谁触发」写真正发起动作的人或系统
- 输入里每个会改状态的动作都在表里

## 六、补丁包（`--tier patch`）

散修复和小调整，§2 一张表，一行一个需求，表里讲完。某一项涉及新对象、状态流转、跨端不一致，或需要在 §6 交代取舍时，才在表后另起 `## 2.N` 写成模块块，表里该行的验收写「见 2.N 某某」。

完整示例（豆腐块默认文案多语言），§1 和 §2：

```markdown
# 1. 概述

- **要解决的问题**：App 首页直播豆腐块的全局默认文案只有一条简体中文，全球用户都看到中文；运营改不了，每次要提工单改库。
- **本轮做什么**：CMS 加一个入口，运营自己配置 12 个语种的默认文案。
- **成功标准**：待确认（输入未给指标）。

**范围**

| 模块 / 页面 | 本轮改动 | 实施方 |
| :--- | :--- | :--- |
| CMS 直播列表页 | 新增「豆腐块默认文案修改」入口和配置弹窗 | CMS 前端 |
| 默认文案配置 | 按语种存储，存量迁移 | 直播后端 |
| App 首页豆腐块 | 按用户语言取默认文案 | App 客户端 |

- **不做**：单场豆腐块文案（线上已有，行为不变）。

**待确认**

- 迁移后 11 个语种为空，英语也为空。输入一处说空语种显示英语，另一处说英语也空时显示简体中文。暂按「该语种 → 英语 → 简体中文」写，请确认
- 是否在弹窗里展示最后修改人和修改时间（后端会存）

# 2. 本轮需求

| 编号 | 需求 | 端 / 模块 | 改动 | 验收 | 优先级 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 2.1 | 默认文案配置入口 | CMS 直播列表页 | 列表右上「+ 创建直播」左侧加文字按钮「豆腐块默认文案修改」，不用主色实底；点击打开配置弹窗 | 按钮在「+ 创建直播」左侧 | P0 |
| 2.2 | 12 语种配置弹窗 | CMS | 见 2.2 默认文案配置弹窗 | 见 2.2 默认文案配置弹窗 | P0 |
| 2.3 | App 展示优先级 | App 首页豆腐块 | 单场文案 > 全局默认文案（按用户语言）> 英语 > 简体中文 | 用户语言不在 12 种内时显示英语 | P0 |

## 2.2 默认文案配置弹窗

- 12 行输入框，标签用中文：简体中文、繁体中文、英语、俄语、越南语、土耳其语、乌克兰语、意大利语、西班牙语、葡萄牙语、法语、印尼语
- 顶部提示：「12 个语种全部必填，保存后立即生效。」
- 打开时回填已保存的内容
- 保存：12 个语种必须全部填写；有空的 → 拦截并列出未填的语种；全部填写 → 保存、关闭弹窗、提示保存成功，立即生效
- 取消、关闭、点遮罩 → 不保存
- 上线时把现有简体中文文案迁入「简体中文」，其余 11 个为空

**验收**

- 只填 11 个语种时保存被拦截，提示里列出未填的那个语种
- 保存后重新打开，12 个输入框回填保存的内容
- 点遮罩关闭后重新打开，显示的是上次保存的内容
```

本例输入里没提埋点，§7 写一句「本轮不涉及埋点」，看板表删掉。

## 七、§6 决策章

只记输入材料里给过理由的取舍，一行一条，理由照输入写。做法已经写在 §2，这里只写为什么。

```markdown
| 决策 | 理由（来自输入） |
| :--- | :--- |
| 现货频控比合约宽（每日 10 次 / 同交易对 10 分钟） | 现货分批卖出是常态，按合约的频控多数盈利卖出看不到顶飘 |
```

不记进来的：

- 输入只给了结论、没给理由的决策（不替它补理由）
- 自己想出来的「否掉的方案」
- 谁拍的板、中途改过几次

一条都没有就整章删掉。

## 八、§7 埋点章

**表格格式固定，表头一字不改、不增删列。** 推 Confluence 的合并单元格（`--merge-tracking`）和导出 xlsx（`export_tracking_xlsx.py`）都按这一行表头认表，改了就失效，`check_prd_md.sh` 会拦：

```markdown
| 所属页面 | 事件中文名 | 事件英文名 | 属性中文名 | 属性英文名 | 数据类型 | 是否必填 | 数据值示例 | 应埋点平台 | 触发机制 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 直播间 | 策略卡曝光（既有） | `app_live_card_show` | 卡片类型 | card_type | STRING | 是 | market / limit / copytrade | APP / Web | 卡片在悬浮窗内展示后，本期扩展属性 |
| 直播间 | 策略卡关闭 | `app_live_card_close` | 直播间 ID | liveid | NUMBER | 是 | — | APP / Web | 观众点关闭按钮后 |
| 直播间 | 策略卡关闭 | `app_live_card_close` | 卡片类型 | card_type | STRING | 是 | market / limit / copytrade | APP / Web | 观众点关闭按钮后 |
```

**每列怎么填：**

| 列 | 填法 |
| :--- | :--- |
| 所属页面 | 事件发生的页面或模块中文名 |
| 事件中文名 | 已有事件末尾加「（既有）」；新事件不加 |
| 事件英文名 | 用反引号包住；已有事件照抄行为分析平台真名，不改写 |
| 属性中文名 | 已有属性从行为分析平台 `cname` 或域字典抄；查不到写「口径待确认」，是否必填填「否」。不按英文名自己翻译 |
| 属性英文名 | 不加反引号；能复用已有字段就复用（`platform_type` / `is_login` / `liveid` / `upid` / `contentid` / `uid` / `communityId` / `TransPair_current_id`）；新建的用小写下划线，域内已有驼峰习惯（`commentNum` / `giftId`）的跟着用 |
| 数据类型 | 只填 `STRING` / `NUMBER` / `BOOL` / `LIST` 四种之一 |
| 是否必填 | 是 / 否 |
| 数据值示例 | 枚举类写真实取值，用「 / 」分隔（`market / limit / copytrade`）；ID、数字、布尔写 `—` |
| 应埋点平台 | 只填 `APP`、`Web` 或 `APP / Web` |
| 触发机制 | 客户端看得到的时机（「提交成功响应后」「卡片展示后」）；已有事件只加属性时，末尾写「本期扩展属性」 |

**行的规则：**

- 一个事件有几个属性就写几行，所属页面、事件名、平台、触发机制每行重复填（md 表格不能合并单元格，推送时脚本会合并）
- 只有本期新增或扩展的事件进表，没变的已有事件不列

**只做 APP / Web 端埋点。** 服务端和管理后台（CMS）不埋点，后台操作走操作日志。服务端只负责把结果或状态送到客户端，客户端看到后上报。某个事件客户端根本看不到（比如后台任务状态变化），就不设埋点，在 §1 待确认里写一句告诉数据团队。

**起事件名前先查证**，按顺序，不凭记忆起名：

1. `python3 projects/sensors-metrics/scripts/probe_event_properties.py --events <候选名>`：行为分析平台里已有就是既有事件，照抄真名、真属性、真取值
2. 查 `projects/sensors-metrics/references/events-{域}.md`，照域内同类事件的命名起名（范式见同目录 `event-naming-conventions.md`）
3. 域内没有先例才用 `{前缀}_{模块}_{动作}`：曝光 `pageview_`、App 点击 `appclick_`、Web 点击 `webclick_`、提交 `app_*_submit`、成功结果 `app_*_success`、状态变化 `app_*_status`，并在表前注明「域内无先例」

表前一句固定写：「事件名与属性名为本轮拟名，待行为分析平台注册后回填真名。」（全是既有事件时不写）

**看板口径（7.2）：**

```markdown
| 指标 | 计算口径 |
| :--- | :--- |
| 策略卡点击率 | 策略卡点击事件去重用户数 / 策略卡曝光事件去重用户数 |
```

- 指标名与 §1 成功标准用同一个名字
- 口径用事件中文名写分子分母，不写 L1、L2 这类缩写

本轮没有埋点：§7 保留，写一句「本轮不涉及埋点」，表格删掉。

## 九、写完后对照输入检查

逐项做，不跳：

1. 把输入材料一条条过：每条规则能在 PRD 里找到对应的一句；找不到的补上
2. 搜每个数字（阈值、次数、时长、百分比）：全文只出现在一处
3. 对照差异表：输入提到的每种情况都有一列
4. 对照状态表：输入里每个改状态的动作都有对应的行（第五节）
5. 搜「见」「按」：每个引用的标题或规则名真实存在
6. 读 §6：每条理由都能在输入里找到原话或原意
7. 读待确认：输入里的矛盾、「待定」「你看着办」都已列进去

测试里弱模型最常出的错，写完重点看：

| 常见错 | 正确做法 |
| :--- | :--- |
| 推新卡写成新卡进入「在架」 | 拆两行：新卡「不存在 → 讲解中」，旧卡「讲解中 → 在架」 |
| 差异表只列本轮新增的情况 | 线上已有的情况也占一列 |
| 同一条规则在规格、§5、状态表各写一遍 | 写在一处，别处写规则名 |
| §6 补了输入里没有的理由 | 没有理由的决策不进 §6 |
| 验收「关闭后不再出现」与规格「讲解中换卡后重新出现」打架 | 验收逐条对照规格，写成规格的边界情况 |
| 引用「见补充说明」，但没有这一节 | 引用写真实存在的标题全名 |
